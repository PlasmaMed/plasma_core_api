# Source identities and master-data change ingestion

`POST /api/integration/legacy/events` accepts a committed source snapshot using the existing server-to-server `X-API-Key` policy. The existing JWT CRUD routes and employee permissions are unchanged.

The envelope uses **snake_case**:

```json
{"event_id":"11111111-1111-4111-8111-111111111111","source":"plasma-bv","source_system":"quanly.plasma.vn","sequence":123,"entity":"customer","entity_id":42,"operation":"update","occurred_at":"2026-10-27T03:00:00Z","data":{"id":42,"name":"Synthetic Clinic","phone_number":"0900000000","address":"Synthetic address","status":"active","old_id":"","deleted_at":null}}
```

`source` is a stable lowercase namespace of 1–40 characters matching `[a-z0-9][a-z0-9_-]{0,39}`. Sequence and entity ID are positive 64-bit integers. Entity is `customer`, `tank`, `engine` or `user` (an employee profile); operation is `create`, `update` or `delete`. `occurred_at` requires an explicit UTC offset. `data` is the complete persisted source row, including its numeric `id`; the ID must match the envelope. The maximum HTTP request size is 1 MiB.

`source_system` identifies the originating application: `quanly.plasma.vn` or `newapp.plasmamed.vn`. `source` remains the stable database/outbox namespace (`plasma-bv` or `newapp` respectively); never rename an installed namespace or reset its sequence. The namespace is permanently bound to one source system. Only the original `plasma-bv` client may omit `source_system` for compatibility. The same numeric ID in the two applications is independent. The receiver checks `data.id == entity_id` and, if the sender supplies optional `core_id`, requires it to equal the already verified mapping. A supplied Core GUID never establishes ownership.

Core keeps its native GUID `Id` and adds nullable `QuanLyId` and `NewAppId` columns to **Customers, Tanks, Engines and Employees**. Read DTOs expose `quanLyId` and `newAppId`; employee-login DTOs read them through their employee profile. Ordinary create/update DTOs cannot write these columns. The unique source-ID indexes include native soft-deleted rows to prevent accidental ID reuse. For deduplicated customers the columns hold one stable representative ID, while **LegacySyncMappings** retains every source alias and its deletion state. No original Mongo `LegacyId` field is repurposed.

`GET /api/legacy-sync/mappings/{entity}/{coreId}` returns `ApiResponse.data` as `[{source,sourceSystem,entityId,isDeleted}]`. It requires the matching module's View permission and honors machine row access. Use the native **employee profile** GUID with `entity=user`, not the EmployeeUsers login-account GUID. Snapshots and credentials are not exposed by this endpoint.

Successful responses are a raw acknowledgement, with no `ApiResponse.data` wrapper:

```json
{"event_id":"11111111-1111-4111-8111-111111111111","source":"plasma-bv","sequence":123,"status":"applied"}
```

Status is `applied`, `duplicate` or `stale`. A pending original `plasma-bv` event whose receipt predates `source_system` may be retried by an upgraded sender with the domain added: the receiver accepts only the original content hash with that one envelope field omitted. Changed event data, IDs or optional `core_id` still conflict. Repeated event IDs with identical normalized content repeat acknowledgement; the same event ID with different content, or reused source sequence with another event, returns 409. Older per-entity sequences receive `stale` without changing native records or the latest snapshot. Receipts, the current snapshot, mappings and native changes commit together. A short PostgreSQL advisory transaction lock protects first-time identity matching and administrative mapping from concurrent receivers. The sender retains failures for retry. Never mark delivery from HTTP status alone: match all acknowledgement identity fields.

## Deployment and authoritative identity bootstrap

Apply EF migrations `20261027030442_AddLegacySyncIngestion` and `20261027032418_AddExternalSourceIdentities` before enabling source delivery. It creates `LegacySyncMappings` and `LegacySyncReceipts`, then copies existing authoritative `plasma_migration.customer_map` and `plasma_migration.tank_map` rows into the namespace **`plasma-bv`**, preserving numeric source IDs, native GUIDs and the previous `source_data` snapshot. The first migration does not modify native customer/tank rows. The second adds the source-ID columns and backfills them only from verified mappings. It also bootstraps `newapp_migration.customer_map.target_id` and verified employee entries in `newapp_migration.user_map.employee_id` (the latter is a profile GUID, unlike `target_id`, which is an account GUID). Raw source user credentials are excluded: only supported public profile fields enter the new mapping snapshot. Missing native targets, contradictory ledgers and ambiguous source-system IDs abort migration transactionally. No persistent verified NEWAPP engine/tank or Quanly engine/user ledger is assumed to exist: those existing identities require an audited explicit bind before update delivery. Never derive ownership from numeric code suffixes or transient staging tables. An absent historical mapping schema is permitted on a new installation; existing source updates then require verified explicit mappings. Review the bootstrap and production source namespace before deployment.

Customer mappings remain **many-to-one** after historical deduplication. Mappings with multiple source aliases, or identified as survivors by `plasma_migration.customer_merges`, preserve canonical native values. No customer is matched by name or telephone. Historical tombstones are never guessed to be active identities. Tank, engine and employee-profile mappings are unique per source namespace and native record; a native record can be explicitly bound to the other application as well. Physical serial/code/old-ID matches are collision checks and cannot authorize an update. For example `KC0001` and `KC1` identify a collision requiring reviewed binding rather than a new tank. Missing or conflicting mappings return 409 and remain in the source queue. Changes to a mapped asset's physical identity are also checked against other native records.

A source `create` can create a new native customer/tank/engine/employee profile and its mapping. An ordinary unmapped `update` cannot allocate a native record. Plasma BV customer codes use `PLASMA-C{id}` as in the prior importer; new tanks use their source serial for the native code when it fits. Existing native codes, legacy identities, unrelated tax/contact/account fields, employee assignments, manufacturer and inspection fields are preserved. A previously source-deleted customer that was never imported may be restored only from the original authoritative `plasma-bv` null-target migration mapping at revision zero; its allocated native ID is persisted. An unknown `delete` for any entity creates a null-target identity tombstone without looking up or mutating native rows (including a source INSERT+DELETE in one transaction). A later unknown `update` still returns 409; an explicit `create` may allocate a new native record after physical collision checks.

Administrative binding is available at `POST /api/legacy-sync/mappings` with `{source,source_system,entity,entity_id,core_id}`. It requires an employee JWT with the corresponding module's Import permission: Customer, Tank, Engine, or Employee for `user`. The integration API key cannot bind identities. This call only adds verified ownership or resolves a null-target tombstone; an existing non-null mapping cannot be reassigned. Resolving a null target retains its source sequence, deletion state and snapshot until the retained source event retries; source-ID indexes and alias safeguards still apply. Explicitly adding a second customer alias marks all aliases across both systems as canonical-preserving. Deleting one asset or employee alias cannot delete the native record while another active verified identity remains. Use a reviewed maintenance procedure if a later native deduplication changes canonical GUIDs. Do not rerun the old direct importer concurrently with the new receiver: its independent tables do not track receiver revisions.

## Projection rules

Customer `name`, `phone_number`, `address` and `active`/`inactive` status project to native name, phone, address and status. Native `Suspended` is preserved. For a merged canonical customer, a source field must actually change since that alias's previous snapshot and all active alias values across both systems must normalize to the same value before it changes the native field. Conflicting alias values remain in source snapshots. Native canonical Active status is preserved against alias-only downgrade. Deleting a merged source alias records its tombstone without deleting the native survivor. Deleting an unmerged customer follows Core's restriction against deletion while native tanks remain assigned, and soft-deletes its customer accounts together.

Tank `customer_id` must resolve through an active customer mapping. An unresolved customer reference rejects the entire event. `_capacity` metadata (`id`,`name`,`value`) updates native capacity; a new tank requires it and initializes unit `L`. Its type is initialized from capacity name only for new native rows. `_warehouse` and `_factory` contain resolved `id`/`name` values; an `occupied` tank uses its mapped customer's location before a stale source warehouse value. Other states use warehouse, customer, then factory. Complete metadata with all location references cleared clears the location. Unenriched older snapshots preserve the native location.

Established status mappings remain compatible with the previous importer: `occupied→AtClient`; `ready→InStock` unless assigned to an employee, then `Available`; `empty`/`to_be_refill→Empty`; `broken→Damaged`; `loading→Loading`; `locked→Locked`; `disabled→Inactive`. Recognized intermediate workflow statuses preserve the current native status and remain fully represented in snapshots. A deleted native tank cannot be restored using such an unmapped intermediate state; it returns 409 until a supported transition is available. New source unknown status values return 400 rather than being silently coerced.

Engine full snapshots contain `id`, `name`, `serial`, optional `version`/`old_id`, and normalized `status`. Status maps `active→Active`, `inactive`/`locked→Inactive`, `broken→Broken`, `checking→Checking`, `repair→Repair`. The source version remains in the immutable snapshot; native model, owner, employee assignment and warranty fields remain managed in Core. Existing mapped native GUIDs are checked before every update. A source deletion cannot delete an engine with a running native session.

User snapshots are an allowlist of `id`, `name`, `email`, `phone_number`, boolean `is_active`, optional descriptive `user_type`, `deleted_at` and audit timestamps. Senders capture only internal staff (not customers, device accounts or third parties). They create/update an **Employee profile** and never create, update, delete or authenticate an EmployeeUsers login account. Passwords, hashes, salts, tokens and roles in a user snapshot return 400 before receipt storage. Native OnLeave/Resigned status and non-source profile fields are preserved. Employee permission caches are invalidated after the committed profile event (including repeated acknowledgements), so inactive profiles do not retain stale cached access. A source event cannot deactivate/delete a Core Super Admin, or delete a profile with assigned assets. A role transition back into internal staff sends explicit `create`, preserving a previously verified native GUID.

All source-only fields, RFID, numeric warehouse/factory/order references, metadata and relationship ID arrays remain intact in JSONB snapshots and immutable receipts. No source account password/hash/token data should be included in these snapshots. A `delete` event or non-null source `deleted_at` soft-deletes the mapped record; no physical native row is removed. A native tank currently `InUse` rejects deletion until use ends. A source delete can acknowledge an already native-deleted record without reviving it; ordinary source updates cannot silently revive records manually deleted in Core.

Production uses HTTPS and the existing shared server secret. Keep real keys out of source control, browser code and logs. The current deployment documents same-host `/etc/hosts` resolution for `api-core.plasma.vn`; retain its hostname and normal TLS validation.

## Isolated verification

```sh
TEST_PG_CONNECTION='Host=127.0.0.1;Port=5432;Username=local_test_admin;Database=postgres' \
  dotnet run --project scripts/LegacySyncTests --disable-build-servers
```

The test runner accepts only loopback or `/private/tmp/` PostgreSQL sockets, creates a unique `core_legacy_tests_*` database, runs real migrations and synthetic HTTP receiver cases, and removes only that owned database. It never starts production initialization or seeds, connects to Production, or sends source production data to Core. It checks real migration bootstrap from both verified ledgers, source-ID read DTOs, per-module metadata authorization, separate same-number identities across systems, all four entity types, optional Core-ID rejection, physical collision rejection until bind, upgraded receipt retry compatibility, cross-system alias preservation/deletion, credential rejection, capacity/customer projection, transactional rollback and safe tombstones/restore handling. `DesignTimeDbContextFactory` keeps EF schema tooling separate from web-host startup, workers and database seeding; `CORE_DESIGN_CONNECTION` is an optional schema-tool connection override.


## Exact stream selection and shared-record authority

`LegacySync:AllowedStreams` is an optional array of `{ "Source": "plasma-bv", "Entity": "customer" }` pairs. When configured, the receiver requires an exact pair **and** membership in the existing `AllowedSources` / `AllowedEntities` arrays when those older arrays exist. Omitting the matrix preserves the older selection behavior; an explicitly empty matrix denies all streams. Unknown entities, invalid source namespaces and duplicate policies fail configuration validation. Configuration is server-side; these examples do not change production settings.

`LegacySync:ProjectionOwners` optionally chooses the source namespace that may project each shared `tank`, `engine` or `user` record, for example `{ "tank": "plasma-bv", "engine": "newapp" }`. It applies when a native GUID has verified identities from multiple source namespaces, including retained tombstones. Without an explicit owner, a new event for such a shared asset/profile returns 409 rather than choosing the most recently received source. Existing single-source records keep their behavior. The configured owner must have a verified identity for the shared record.

For an alternate source, a successful `applied` receipt means its mapping snapshot/revision/tombstone was stored; native business fields are preserved. The primary source still projects its new state. The existing deletion guards remain in force. Customer aliases use their separate canonical/consensus rules and cannot be assigned a projection owner through this setting. Neither rule creates login accounts or copies credentials.
