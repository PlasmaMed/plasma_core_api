Source sync receives complete PostgreSQL text-value snapshots and committed changes over HTTPS at `/api/integration/source-sync/{source}`. It is disabled by default. Existing entity and history endpoints keep their contracts.

Configuration is private runtime configuration under `SourceSync`: `Enabled`, a dedicated raw-role `ConnectionString`, and `Sources.quanly` / `Sources.newapp` with `InstallationId` and a distinct 32–512-character printable-ASCII `Key`. The existing integration API key is also required. Do not change installed capture identities; a 32-hex PostgreSQL installation ID and the corresponding hyphenated UUID are the same value.

Run `install.sql` explicitly with a reviewed administrator connection before enabling the receiver. It creates only `source_sync` controls and the two raw schemas, and refuses an unowned control schema. Snapshot begin creates only manifest-owned raw tables under `source_quanly` or `source_newapp`. Existing tables from another mirror are **not** silently adopted; they require an audited namespace/ownership migration. A runtime principal needs no dbo DDL or native data rights. Raw schemas can contain source account data and must remain inaccessible to browser/API business principals.

All payload field names are camelCase. Source IDs are only `quanly` and `newapp`. IDs, transaction IDs and completion row counts are canonical decimal strings. Rows contain the exact registered column names, each a PostgreSQL text string or null. The receiver never parses JSON/array/numeric/date source column contents. Limits: 16 MiB per request/part, 5000 snapshot rows, 1000 events per part, 512 columns. Larger closed source transaction prefixes use multipart staging and one atomic background apply.

Begin body: `{installationId,generation,snapshot,tables:[{name,columns,primaryKey,catalogSignature}]}`. Rows body: `{installationId,generation,table,chunkId,rows}`. Complete body: `{installationId,generation,tables:[{name,rowCount}]}`. Events body: `{installationId,generation,batchId,events:[{id,transactionId,table,operation,oldRow,newRow,occurredAt}]}`. The timestamp ends in `Z`; operations are uppercase INSERT, UPDATE, DELETE, TRUNCATE. Old/new images must be null when inapplicable. The publisher filters events already visible in the PostgreSQL baseline before submitting changes.

Snapshot chunks use transactional SqlBulkCopy into manifest-owned heaps, storing immutable chunk digests/receipts together. Complete returns HTTP202 with status `finalizing`. A durable background finalizer streams each whole table once, verifies actual values/key/row hashes and count plus commutative SHA256 sum/XOR against chunk digests, then builds indexes with MAXDOP2. Restart resumes per-table phases. Native projection and new event application wait for status `ready`; a bounded `errorCode` makes a failed finalization visible.

For a large event prefix, `POST events/parts` accepts `{installationId,generation,batchId,partIndex,events}`. Its ACK contains exact event IDs and `staged` or `duplicate`, which does not prove application. `POST events/commit` accepts `{installationId,generation,batchId,partCount,eventCount}` and returns202 `queued`. Parts must be contiguous from0 and globally ordered by event ID. `GET events/{batchId}` reports queued/applied/failed, counts and a safe error code. After whole-batch `applied`, `GET events/{batchId}/parts/{partIndex}` acknowledges that part's exact IDs. A background transaction applies all parts/receipts and marks the batch applied together; a malformed later part leaves no earlier mutations or receipts. Incomplete or failed predecessor jobs block later jobs. Staged payloads remain immutable across crashes and retries.

Raw rows and receipts commit atomically, with exact actual before-image checks. Identical chunks/events/batches retry idempotently; changed immutable deliveries return409. A seeding generation can be restarted under the same installation; finalizing/ready generations require an explicit reviewed rebaseline. The previous PostgreSQL worker's `delivered_at` is not an HTTP delivery marker: publishers must keep independent consumer state.

Status returns only source identity, generation, readiness/table count and native projection state/count. A raw `applied` acknowledgment proves raw preservation, not native business projection. The internal `ISourceSyncRawReader` exposes durable events and a consistent selected-table snapshot to explicit native adapters. Unsupported and blocked projections remain visible and do not mutate native ACLs or guessed identities.

Pure contract checks: `dotnet run --project SourceSync/validation/SourceSyncContractTests.csproj` from the API project directory. For real SQL cases, supply `SOURCE_SYNC_TEST_SQL` only for loopback database `core_source_sync_validation_20261109` with database extended property `core_source_sync_validation_owner=core-source-sync-validation-v1`. The runner refuses a reused database and never creates/deletes databases. It exercises bulk snapshots/finalization, idempotency/conflicts, PK changes, keyless duplicates, rollback, truncate, a1001-event multipart transaction and a malformed second part rolling back the valid first part, preserving a native dbo sentinel. HTTP authentication/proxy/crash validation is additionally required before enabling Production.

Read-only end-to-end comparison: add `SOURCE_SYNC_COMPARE_REPORT=/fixture/private/fixture-report.json` with the same guarded SQL connection. This branch skips all fixture installation/DML, checks the report's quanly binding/catalog against SQL, streams actual raw column values and compares count plus SHA256 sum/XOR to PostgreSQL report digests. Output contains only bounded counts/table metadata; source values and credentials are never printed.
